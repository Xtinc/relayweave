# 会话数据任务改造计划

初版：2026-11-03；本轮改造：2026-11-04

## NodeSession 职责收拢（已实施，2026-11-04）

本节记录本轮实施方案。目标是让 NodeSession 自己主持会话，从代码主流程直接读出建立、转发和退出顺序；保留已经建立的数据执行域边界。生产结构与文档已完成迁移，受影响测试、完整构建、UDP 重复验证及最终完整回归均通过；实施和验证记录见本节末。后文保留前几轮已完成的数据任务改造、所有权审计和 AsyncEvent 实验记录，其中关于保留控制器阶段转发接口的旧结论由本节替代。

### 1. 改造前的问题与最终结构

改造前 NodeSession 保存会话资源和控制器，run/消息入口又转发给 ControlRouterSingle/Multi；控制器持有 NodeSession& 并以 friend 访问其私有成员，再调用 NodeSession 的数据操作。两个控制器分别负责异常、停止与收尾，数据阶段又经 NodeSession 转发到 SessionTransfer。流程和状态分属不同对象，存在不必要的往返依赖。

确定按以下结构收拢：

- **NodeSession**：唯一的控制流程主体，负责请求身份、建立期限、Agent/peer 消息、Flow 事务、Ready、取消原因，以及停止并等待数据任务。
- **SessionTransfer**：保持独立，在固定 transfer executor 上负责一次安装、准备、激活、转发和资源释放；不借用或回调 NodeSession。
- **RelayTransport / NodeLinkMgr**：继续提供各自资源操作与 Flow 管理，不承接会话控制状态。

撤销 ControlRouterSingle/Multi 两个行为对象。差异字段收进 NodeSession 私有的 Single / Multi 按值记录，以 std::variant 表达互斥模式。它们只有数据，不持有 NodeSession&，不启动协程、不分发消息、不拥有取消或清理流程。模式在构造后固定，不在任何 await 或关闭期间替换。

这个 variant 只区分两种业务数据，不再以 visit 为每个入口做行为转发；公共流程直接执行，仅在单/多节点确有差异的位置做局部分支。不新增虚控制器、生命周期钩子接口、Context/Runner/Coordinator 等包装对象。

### 2. 状态归属与变量寿命

| 数据或对象 | 唯一归属、访问范围与释放时点 |
|---|---|
| NodeSession | RelayNode 的会话容器以 unique_ptr 独占持有。根控制任务及其同域子协程借用；根 co_spawn 完成处理器最终移除。取消请求不移除实例，也不提前释放容量。 |
| node_ | 必需的 RelayNode& 借用。根任务的现有 Node 保活覆盖其访问；Node 先排空会话，再停止 NodeLinkMgr 和数据管理器。 |
| protocol_、service_、request_id_、deadline_ | NodeSession 按值持有。两个控制器中的公共字段移到此处，仅存一份。deadline_ 在构造时按配置计算一次，整个建立流程共享同一绝对期限。 |
| Single | 仅存 consumer / producer 的 AgentPeer，允许二者指向同一 Agent。无需保存 Multi 字段或无意义占位值。 |
| Multi | 仅存本端 AgentPeer、ingress、path、peer、epoch、flow_id、accessor，以及 peer_prepared / peer_finished、from_peer 和 changed 定时器等多节点协调数据。它不再存一份公共 service/request/deadline/reason。 |
| RelayRequest 与控制消息 | RelayRequest 仅是构造输入，字段移入确定的持有者后释放，不同时保留原请求和另一套字段。消息处理不将调用方的 CtrlMessage/njson 引用保存到后续协程。 |
| AgentPeer 与地址字符串 | 按值存 AgentPeer；本地控制连接仍弱借用，远端仍按 primary/session 身份及失效通知管理。异步任务需要的地址/accessor 在当前控制调用内复制为 std::string，不把 peer() 返回的 string_view 跨 await 保存。 |
| endpoint_ | 控制面的 AttachResult 值副本，由 Installed 赋值，保存到会话收尾结束。它只保存凭据，不持有 pair/socket。uuid() 从这里取得，不增加 uuid_ 或 installed_ 镜像字段。 |
| 业务进度与停止原因 | NodeSession 持有一份 Progress、stage_ 和可选 close_reason_；原因存在即表示进入结束流程。首个失败/停止原因不被后来的取消错误覆盖；普通成功结束仅在没有失败原因时记录完成原因。 |
| traffic_ | 尚未启动数据任务时由 NodeSession 暂存；创建数据任务时移交 SessionTransfer::Setup，再由准备操作移交 pair。会话不另留共享副本。任务未启动的失败路径随会话释放暂存值。 |
| transfer_ | NodeSession 持有唯一的数据任务入口，最多创建和 start 一次。任务尚未创建是正常可能状态，例如提前取消或 Flow 建立失败；收尾处的判空是资源存在性判断。 |
| SessionTransfer 的共享持有 | 保留当前 shared_ptr：会话、原生 co_spawn 完成处理器、尚未执行的停止投递确有独立寿命。后两者可能晚于会话析构，仅访问 Task 自身；不捕获 NodeSession，不在晚到处理里访问借用管理器/协议。 |
| Setup、阶段事件与授权 | Setup 是移交数据任务的一次性初始化记录；epoch/flow_id/期限的跨域值副本有明确用途，不是第二个控制状态。Event/State、继续通知与授权去重仍只由 SessionTransfer 管理，不复制到 NodeSession。 |
| pair/socket/UUID/计费访问者 | 管理器保存资源对象，SessionTransfer::run 管理业务寿命，并在自己的执行域释放。Finished 只代表转发结束；多节点 peer Finished 协调完成前仍保留端点。 |
| Flow 事务 | ingress 记录成功取得的 epoch/flow_id，并负责退出时 close_flow；egress 使用已授权 Flow，不额外争夺事务关闭责任。返回的 Flow 身份必须先记录，再检查取消/epoch，保证已取得的事务有收尾依据。 |
| 只供一个阶段使用的值 | Flow 返回值、临时通知 JSON、已选 transport 引用、角色和一次通知结果优先使用局部变量。跨 await 的局部值由所属协程帧持有；不为跨函数方便统一提升为成员。 |

构造严格按成员声明顺序初始化；Single/Multi 的构造只接收显式值和 executor，不接收 *this，不读取尚未构造完成的会话成员。RelayRequest 各字段的移交顺序明确，不在整体 move 后继续读取其字符串或路径。

Progress 沿用现有协议里程碑，统一 Opening / PeerOpened / AgentNotified / Ready；单节点跳过仅多节点使用的 PeerOpened。它记录已经到达的业务阶段，包含进入 Agent 通知阶段这一事实，以覆盖部分通知提交后失败的收尾。删除 Single::ready_，就绪统一由 Progress::Ready 表达。退出事实由 close_reason_ 是否存在表达：已经 Ready 与正在退出可以同时成立，收尾需要知道历史进度；无需另存停止布尔值。取消不将 Progress 改成 Closing，也不再叠加 stop_requested_/closing_/failed_/finished_ 等同义状态。数据任务的 State 表达另一执行域上的任务寿命，不能与业务 Progress 合并。

### 3. 主流程和必要的并发

NodeSession::run 成为根控制协程，直接看到异常处理与完整收尾；入口 Flow 建立直接写在 MultiSession::run 的入口分支，公共建立与转发由 establish_and_transfer 负责。结构如下，名称为流程示意，不要求每一步都拆成函数：

```text
NodeSession::run
  已请求停止：进入统一收尾，不启动新业务
  Multi ingress：在原始期限内等待 open_flow，记录 Flow 身份，再通知 peer open
  Single：直接等待本会话建立与转发
  Multi：本会话建立与转发，与 Flow 关闭监视组成原生 parallel_group
         任一完成，取消并等待另一个退出
  捕获业务失败，保留首因
  屏蔽根任务取消
  按原有协议顺序通知关闭、停止并等待数据任务、释放 ingress Flow
  根任务返回；由 RelayNode 完成处理器移除 NodeSession
```

业务推进只保留一条公共顺序：

1. 公共建立协程直接选择 transport、移交 Setup、启动唯一数据任务，等待 Installed 并保存 endpoint。
2. 根据模式通知单节点的两个 Agent，或多节点的本端 Agent；业务进度记录必须保留现有部分发送失败的处理语义。
3. 直接等待 transfer_->prepared()。单节点继续；多节点按 ingress/egress 执行必要的 PeerAttached/PeerReady 协调，沿用绝对建立期限。
4. 直接等待 transfer_->activate()，确认实际激活；在 Ready 的外部副作用前检查停止/期限，再发送原有 peer/Agent Ready 并记录业务就绪。
5. 直接等待 transfer_->transfer()。单节点进入收尾；多节点发送 PeerFinished，并在现有 disconnect_timeout 内等待对端 Finished。
6. 数据资源持续存活到根流程明确停止并等待任务退出，不能在收到 Finished 时提前销毁。

删除 prepared()/activate()/transfer() 这些仅转发的 NodeSession 方法。保留有实际职责的消息匹配、授权入口、通知编码和必要的 peer 协调函数；不把每一行改写成一个私有接口，也不创建两套相似的 Single/Multi run 流程。

并发只保留当前必须存在的边界：数据任务一次 co_spawn；Multi 控制域内一个原生并行组监视 Flow 关闭；停止时一次向数据 executor 投递取消。建立期限所用的同控制域 co_spawn/cancel_at 保留操作级取消作用域，不能机械内联成影响整个会话的期限。实际 Flow 绑定到协议执行域的原生调用维持原有资源归属。本次不自写 awaiter、完成 token、任务计数排空器或组合框架。

### 4. 退出顺序和责任

所有入口最终回到 NodeSession::run 的同一收尾段。停止入口仅记录首因、请求取消并唤醒多节点协调等待，不直接删除对象、释放 Flow 或关闭数据域 pair。Flow 监视协程保留原并行组的取消与排空语义，返回前记录关闭原因，避免另建一条独立清理链。

| 情形 | 收尾顺序与需要保留的行为 |
|---|---|
| 单节点 | 屏蔽根任务取消 → 停止并等待数据任务 → 按原规则通知 Agent 关闭/建立失败。已 Ready 的流式正常结束仍依靠数据 EOF；UDP 保留控制关闭通知；同一 Agent 不重复 Ready。 |
| 多节点 | 同控制域的建立/转发及 Flow 监视子协程先被取消并排空 → 屏蔽根任务取消 → 依原进度通知本端 Agent，必要时发送 PeerClose → 停止并等待数据任务 → ingress 释放已取得 Flow。 |
| peer 发起关闭 | 保留 from_peer，避免回发重复 PeerClose；仍必须等待数据任务结束。关闭中的会话继续消费匹配的 peer 消息，直到根任务结束，不能将迟到消息误当成新会话。 |
| 安装前失败/提前取消 | 无 transfer 时跳过数据停止；无已取得 Flow 时跳过 Flow 释放。已有的错误/关闭应答规则按真实进度执行，不伪造安装成功状态。 |
| Finished 后仍等待 peer | 使用有限收尾期限；超时、控制断线或停机都能打断等待，并走同一个停止与排空路径。 |
| Node 停机 | 请求所有会话停止 → 等待会话容器排空 → 停止 NodeLinkMgr 和数据管理器。关闭中的会话继续占用原容量，避免过量接纳新业务。 |

根任务只在统一收尾入口禁用取消一次；SessionTransfer::stop 继续要求调用方已禁用取消，数据任务在自己的清理段单独禁用取消。不能把“已发出停止请求”当成“数据任务已结束”。

关闭通知沿用现有尽力提交语义，提交失败不能阻断后续数据排空与已取得资源的释放。保留 Flow 关闭等明确可失败操作的处理；不为每一条内部语句增加 catch、重试或成功兜底结果，不新增通用 Finalizer/StopContext 对象。

### 5. 检查的保留与删除依据

保留外部输入和异步边界上真实可能变化的事实：字段/角色解析、Agent 身份、peer 的 source/epoch/flow_id、重复 open 的内容一致性、ticket/connection_id 有效性、原始建立期限，以及有 await 后外部副作用前的停止检查。attach 身份/ticket 在会话入口统一验证一次，角色授权去重仍由 SessionTransfer 处理；两者检查不同事实，不互相复制。

必须区分检查位置，不能仅因两行条件相似而删除：期间有 await、状态可被消息处理改变时，在发送 Ready 等副作用前的检查有必要；同一同步片段已保证的条件则无需再查。

清理以下冗余：

- 控制器与 NodeSession 的相互转发，以及 Single/Multi 各自重复实现的停止、错误和期限流程；删除两个控制器的 friend 和 NodeSession& 回指。
- 已由固定模式保证的重复 is_multi/variant 类型试探；一个入口确定模式后在该分支直接使用对应记录，模式不是异常回退开关。
- 内部确定已安装、已创建任务的阶段调用，不再层层判空、猜测 AttachResult 类型或静默返回成功。必要的不变量用断言表达，只有入口匹配和实际可缺省资源在所属位置保留判断。
- 不同时保留 ready_ 与 Progress::Ready、独立 uuid_ 与 endpoint_、is_multi_ 与模式 variant、initialized_ 与 transfer_、第二套 Flow 所有权标记与 ingress/有效 flow_id。
- 不创建综合 SessionState 镜像数据任务 State/Event，不为一次状态传播增加新 Event/Context 结构。

### 6. 文件安排与实施顺序

类型及会话逻辑集中在现有 node_session.h / node_session.cpp。Single/Multi 是 NodeSession 内部模式数据；SessionTransfer 继续放在同一对文件中。删除 control_router_single.h/.cpp、control_router_multi.h/.cpp 及对应 CMake 条目，不新增一类一文件的目录或控制器基类。node_common.h 中的 RelayTransport、RelayRequest、AttachResult 等既有契约保持位置和含义。NodeSession 对 RelayNode 的构造与公开入口契约保留；RelayNode 的创建、容量、消息路由及根任务完成后移除的责任不转移，也不增加工厂或代理。

- [x] **先迁移数据与依赖**：把公共字段移入 NodeSession；将差异字段改成私有按值模式记录；保持初始化/移交顺序，取消回指和 friend。
- [x] **收拢根任务与停止入口**：NodeSession 直接拥有异常、停止原因和收尾；搬回 Multi 的 Flow 取得及并行关闭监视；保留进度与阶段对应的关闭顺序。
- [x] **合并业务顺序**：公共安装、通知、准备、激活、Ready、转发只表达一遍；在必要位置保留 peer 分支；删除数据阶段转发方法。
- [x] **迁移消息与删除旧层**：公共匹配/停止入口在 NodeSession，模式内只保留差异数据；删除旧控制器文件/CMake 条目，搜索清理旧名称、重复字段和无人使用的方法。
- [x] **验证与同步文档**：复用和补充现有行为测试，构建、回归、检查资源回收，再按最终代码更新架构说明；不把迁移中的临时包装保留在最终结构。

### 7. 验证与验收

优先扩展已有测试文件，不建立新的测试框架或反射式状态矩阵：

- node_relay_capacity：模式固定、未安装时重复/冲突消息、正确与错误身份、首因保留、关闭中的容量与 peer 消息消费、同一 Agent 的角色。
- session_transfer：继续验证只启动一次、入口前取消、安装/绑定失败、激活门闩、双向 FIN、任务共享持有的必要性，以及 pair/UUID/计费访问者回收。
- node_flows/node_links、node_shutdown、cluster_integration：Flow 成功取得后恰逢取消或 epoch 失效、ingress/egress 关闭责任、Flow 监视打断建立/转发、停机排空；优先使用现有夹具的确定性安排，不用随意 sleep 制造竞态。
- relay_paths 等已有集成：TCP/TLS/UDP 单节点和多节点完整顺序，Ready 晚于激活，PeerFinished 协调期间资源保留，控制/peer 断线和超时退出。

每个补充用例验证外部行为和资源归属，不复制实现分支，也不为纯字段搬移单独写测试。先运行受影响用例，再完成全量构建及现有 CTest；在最终结果之前不宣称计划已完成。

验收时从 run 出发应能直接读出整条会话顺序；每个成员能说明谁读写、为何跨 await 保留和何时释放；控制侧和数据侧各自仅一个清理所有者；没有控制器回调会话、层层转发、逐阶段跨域任务或重复的完成/停止状态。生产行为、网络协议、容量和计费语义保持原样，AsyncEvent 的两项优化及既有数据任务边界不在本轮重构范围内。

### 8. 实施与验证记录

已将公共控制状态和 run() 收回 NodeSession，Single/Multi 仅存按值差异数据；删除两个控制器的四个文件、CMake 条目及 friend。数据阶段转发方法已删除，SessionTransfer 的实现与重构前逐字比对相同。Flow 返回失败时不会覆盖已经记录的首次取消阶段。

现有 node_relay_capacity 增加 Single、Multi ingress/egress 启动前取消用例，仅运行控制执行器即可结束，并检查首因保留、会话销毁后暂存计费引用释放。受影响的 node_relay_capacity、session_transfer、node_shutdown、relay_paths、node_flows、node_links 六项全部通过，耗时 59.28 秒。全部目标已构建成功，无编译警告。

第一次完整回归为 51 通过、1 个 UDP 段错误、1 个 ICMP 跳过。随后在独立重复运行的第 18 次取得 core，堆栈表明测试异常路径先 stop 各执行器，留下持有 Node 的处理器，最终在 control_io 析构期间释放 NodeMetrics 时访问了已析构的 UDP 定时器服务。统一为成功/失败都先 server->stop、再等待线程退出后，第 37 次重复运行正常报告原始断言：UDP TX payload bytes were counted incorrectly。

原断言把客户端收到 UDP 数据当成服务端发送完成后的统计已经更新；UDP 发送完成计数与控制查询位于不同执行器，没有这项顺序保证。测试改为在同一绝对观察期限内逐次查询精确计数，超过预期立即失败、期限内仍不足也失败；不增加固定 sleep，不改生产 UDP 计数或转发时机。异常路径的 Node 排空与执行器销毁顺序也已修正。此定位解释本轮复现，不据此断言没有保留堆栈的历史异常均为同一根因。

最终验证：

- `cmake --build build -j2` 全部目标构建成功，无编译警告；UDP 测试侧修正后单独重建该目标成功。

## 目标与边界（已完成的数据任务改造）

NodeSession 为每条业务会话只启动一次数据任务。控制器始终在 control_io 协调 Agent 与 peer；数据任务始终在对应的 transfer_tcp_io / transfer_udp_io 顺序完成资源安装、接入、Flow 绑定、激活、转发与关闭。TCP 与端到端 TLS 共用流式接入流程；UDP 保留共享监听器的接入与报文转发方式。现有网络协议、鉴权、业务容量与计费规则不变。

本次不合并执行域，也不把逐阶段跨域 co_spawn 换成嵌套回调。不引入通用 actor 框架；仅增加一个明确拥有会话数据生命周期的 SessionTransfer。

## 状态与通信

- 控制面持有控制器状态和接入凭据的副本，完成身份、角色、ticket 与建立期限检查。
- 数据面持有实际 pair/socket/Flow；数据任务通过 RelayTransport& 借用 Node 拥有的管理器，通过可空 FlowProtocol* 借用多节点协议服务，不借用 NodeSession。Node 先排空会话，再停止这些服务。
- 控制面到数据面使用有界授权请求入口及 Activate / Transfer 命令；每个流式角色只接受一次授权，相同请求幂等，冲突请求拒绝。Transfer 在 ready 提交之后发送。关闭使用投递到数据 executor 的取消信号，能够中断接入等待、Flow 绑定及正在运行的 I/O，不依赖转发协程消费命令。
- 数据任务按顺序报告 Installed（凭据）、Prepared、Activated、Finished；唯一的标准 co_spawn 完成处理器在控制执行域确认 Stopped。正常转发完成后等待控制器关闭，以保留多节点 peer finished 协调期间的资源寿命。异常与 Stopped 一起通过通道的原生 `std::exception_ptr` 完成参数传递，由 use_awaitable 自动抛出。
- 所有阶段通知总数固定，通道容量有界。普通 channel/AsyncEvent 只在所属执行域访问，跨域入口使用 concurrent_channel 或平铺的 post。

## 建立与关闭顺序

1. 控制器确定角色、绝对建立期限、计费来源，以及多节点 Flow 信息；NodeSession 启动一个数据任务，等待 Installed 后通知 Agent。
2. TCP/TLS 的授权请求交给已运行的数据任务，由它等待 greeting 完成并绑定 socket，不再为每次 attach 启动子任务。UDP 仍由接收循环验证 ticket、绑定来源地址和通知 attached。
3. 数据任务完成接入及 Flow 绑定后报告 Prepared；控制器完成 peer 协调后提交 Activate。
4. 数据任务实际激活后报告 Activated，控制器再发送 relay.ready。准备阶段沿用原始绝对期限；阶段等待超时或被取消后，控制器必须进入关闭并等待数据任务结束。
5. 数据任务完成转发后报告 Finished，多节点控制器继续完成原有 peer finished 协调。
6. 任意退出路径都停止数据任务并等待 Stopped；数据任务在自己的执行域关闭 pair、释放 UUID 和计费引用。Stopped 之后不再访问 NodeSession，晚到命令不能重新安装资源。

## 结构与生命周期复审

按执行流程、冗余代码、检查及概念重叠三方面复审后，继续简化如下：

1. **完成确认使用 Asio 本身的语义**：Stopped 从 run() 的最后一条手动通知改为标准 co_spawn 完成处理器发出。该单层处理器只更新控制侧状态并通知等待者，不启动任何协程或后续回调。任务在入口前被取消或安装阶段抛异常，也走同一完成路径。
2. **合并状态与通知**：控制侧用 Created / Running / Stopping / Stopped 一个状态替代 started_/stopping_/joined_；删除传输侧 running_/stop_requested_ 与独立 release_ 事件。停止只发出标准取消信号，授权等待、活动转发及正常 Finished 后的最终命令等待均由同一路径中断；通道统一在数据清理时关闭，不再重复关闭输入。
3. **名称表达副作用**：finished() 改为 transfer()，明确该调用在 ready 提交后启动转发并等待 Finished，避免把启动操作隐藏在“等待结束”名称中。保留 Activate 与 Transfer 两个门闩，分别保证 ready 前已激活、ready 提交后才启动流式复制。
4. **减少重叠的数据与错误概念**：NodeSession 与 SessionTransfer 共用 AttachResult；Event 不再同时保存自定义异常字段，直接使用 Asio 支持的异常完成签名。删除 Stream pair 内 producer_id / consumer_id / connection_id 及旧的重放处理，每角色授权去重统一由任务的控制侧入口负责。
5. **删除可信内部路径的重复检查**：移除 NodeSession 重复启动检查、attach 重复角色校验及不可能为空的任务/凭据分支；内部阶段顺序使用断言表达约定。保留网络边界的角色/字段解析、控制身份与 ticket 授权、数据面当前 ticket/连接编号有效期检查和建立绝对期限，它们检查的是不同的事实。
6. **取消屏蔽由收尾所有者负责**：Single/Multi 控制器各自在进入完整收尾前禁用取消，SessionTransfer::stop() 不再重复重置调用方的取消状态；数据任务在自己的执行域屏蔽取消后释放资源。Task 不借用 NodeSession，完成处理器和待执行停止请求持有 Task；停止确认后无业务代码再访问已释放的会话。

边界复查：控制面到传输域只有数据任务启动和停止投递；建立阶段的授权、激活、转发指令及确认通过有界通道传送。多节点 Flow 绑定仍保留一次传输域到 cluster_data_io 的标准 co_spawn，因为 Flow 资源由协议域持有。控制器内用于期限和并行 Flow 监视的 co_spawn / parallel_group 均为原生 Asio、运行在同一控制域；没有新增自定义 awaiter、完成 token、调度器或任务组合器。共享 pair.prepare() 的 attached 等待在 TCP 已就绪时立即返回，UDP 则实际等待接入；它没有重复建立连接或启动额外任务，保留共同契约。

生命周期边界：

| 对象 | 持有者与释放时点 |
|---|---|
| NodeSession | Node 的会话容器独占持有；控制任务借用，控制器停止并等待数据任务、完成 Flow 收尾后，根控制任务完成处理器移除会话。 |
| SessionTransfer | NodeSession、co_spawn 完成处理器及尚未执行的停止投递共享持有；完成处理器覆盖整个 run()，不另加捕获自身的启动函数。数据资源在 run() 返回前关闭，完成处理器确认结束，不借用 NodeSession。 |
| pair / UUID | 管理器查找表持有 pair，数据任务负责其业务寿命；结束时先移除查找关联、关闭 pair，再归还 UUID，最后确认任务完成。 |
| 未绑定 TCP 连接 | StreamPipeline 的 unbound 表及接入协程持有；成功绑定时移交 socket，否则在接入期限、对端关闭或管理器停止时释放。它在绑定前不属于业务 pair；Node 停机另行排空这些接入任务。 |
| 本地 Flow 端口 / Flow 事务 | pair 持有本地端口，数据任务关闭端口；控制器随后完成 Flow 事务释放，协议域统一排空其后台工作。正常 Finished 后保留端点，直到 peer finished 协调结束。 |

NodeSession 的阶段转发接口保留为控制器与数据任务之间的边界，不增加任务或执行域切换。控制器 Progress 表示对 Agent/peer 的业务进展，数据任务 State 表示任务是否已启动、正在停止或已经结束；两者不合并，避免把任务启动误当作业务就绪。

## 管理器多态与共享所有权审计

增加纯虚接口 `RelayTransport`，只定义业务会话需要的 executor、单/多节点安装、准备、激活、转发及关闭操作，带虚析构，不保存资源或共享指针。StreamPipeline 与 DatagramMgr 直接实现该接口，不增加代理层或额外适配对象。SessionTransfer 的 Manager variant、visit、get_if 和具体管理器头文件依赖全部删除；其管理器成员为必需的引用，执行器从管理器取得，不再额外传入一份执行器。

准备接口统一接收授权输入。StreamPipeline 的 prepare 方法消费一端或两端授权、等待 greeting 并绑定 socket；bind 成为私有实现。DatagramMgr 由原共享 UDP 监听器完成 ticket 校验及来源绑定，prepare 等待其 attached 通知，不消费控制授权输入，也不实现无意义的 UDP bind。数据任务始终按安装、准备、激活、转发、关闭的同一流程推进，只区分单节点与多节点业务模式，不再判断 TCP/UDP 具体类型。虚调用位于阶段入口，逐包循环保持原有实现。

## 全量共享所有权复核

审计范围为 node、agent、protocol、proxy 的生产代码。判断依据是「谁在独立等待、容器何时删除、最后一次访问何时结束」，不按成员层数机械替换指针。默认按值或独占持有；借用必须有覆盖其访问的所有者；共享必须能指出容器以外的存活需求。

本次删除的共享关系：

- **NodeSession**：Node 的 vector 改存 unique_ptr；创建后移交容器，完成处理器借用地址，run 完成后删除。取消只请求结束，关闭中的会话继续占用容量，直至数据任务及 Flow 收尾完成。启动失败由原有回滚撤销容器项。
- **ProxySession**：ProxyServer 独占每个会话，stop 只取消 I/O；原生完成处理器结束日志和清理后删除。会话内并行转发在返回前已汇合，无其他独立持有者。
- **ClusterSession / LocalParticipant**：ClusterRoom 独占参与者；远端 reader 排空 TLS 后，完成处理器借用会话并通知 room 删除。room 的 async_stop 等到所有远端参与者退出才返回，删除 ClusterSession 的 enable_shared_from_this 与弱引用完成包装。启动失败先撤销 room 登记。
- **NodeLink 待认证 socket**：握手协程用 unique_ptr 持有；accepting_ 改为非拥有指针集合，只用于停机关闭。启动失败撤销登记；握手正常、拒绝或异常退出都先撤销登记，已认证的 socket 移交 NodeLink。协议 stop 排空握手任务后才允许析构索引。
- **RemoteFlow**：结果与通知直接放在 request_flow 的协程帧中，remote_flows_ 改为借用索引；应答、成员变化和停机同步通知，不转交所有权。ScopeGuard 在协程帧销毁前撤销登记；取消与超时也遵守同一顺序。
- **重复临时持有**：SessionTransfer 启动和 TCP accept_loop 直接传入 awaitable，唯一完成处理器已持有自身，不再额外用捕获 self 的函数包裹；同步激活及 TCP bind 完成 greeting 等待后的 pair 查找改为借用，不复制 shared_ptr。

| Flow 端口 / UDP 接收队列 | Pair 与 FlowState、跨域关闭投递及端口在途操作；UDP 绑定前即可收包，Flow 关闭后端口操作仍需安全返回 | 端口仅弱引用协议；接收队列为独立共享对象，无协议/Flow 回指 |
| PMR 载荷池 | 协议、端口与 PooledBuffer 的 deleter | 每个载荷独占自己的内存块，仅共享分配资源；最后一块归还后才允许销毁池，不反向持有协议 |
| SharedLink / MasterPath / CloseNotice | 事务索引、多个调用者的等待、定时器或释放确认；移除索引后等待者仍会读取结果 | 取消定时器、发布完成/释放事件并撤销索引，晚到定时处理释放事务；事务不强持有管理器 |
| establish_flow 的结果通道 | 父等待与并行 ensure_link 完成处理；父等待取消后子 Link 尝试可继续完成 | 每个完成处理只投递结果并释放通道，不捕获父事务或管理器 |

上述共享表达的是彼此独立的异步使用窗口，不是将整个对象树统一包装成 shared_ptr。尤其不能把 Agent UDP 监听器跨 await 的会话局部变量改为引用，也不能让载荷直接借用协议内存池。已有 Flow 接收测试验证协议能够先于导出的载荷销毁、活动端口任务完成后协议可释放；数据任务测试验证任务不增加管理器持有计数，计费对象完成准备后仅由 Pair 保留。

## AsyncEvent 通知审计与微基准（2026-11-04）

本轮只审计生产代码并运行临时微基准及原型单测，不修改生产通知实现。AsyncEvent 实际是同一执行域的一次性广播锁存器：先通知、后等待也不会丢失；重复通知幂等；取消只影响相应等待者；事件必须覆盖全部 wait 的寿命。它不适用于逐次到来的消息、可重复脉冲或跨线程直接访问。

### 发出端、接收端与频率

生产代码共有 14 处 AsyncEvent 成员定义，其中 6 处属于组件停止/排空，8 处属于建立及业务资源寿命；这不是每条报文都执行 14 次通知。

| 成员 | 执行域 | 发出端 | 接收端 | 等待者与频率 |
|---|---|---|---|---|
| AgentControl::discovery_done_ | Agent control | discovery_loop 的 co_spawn 完成处理器 | AgentControl::close | 通常 0/1；发现任务退出时一次，不是每次发现结果 |
| NodeConnection::stopped_event_ | Agent control | run 完整退出；未启动/无 operations 时 stop | NodeConnection::close | 通常 0/1；整个连接任务退出，不是每次重连 |
| Forwarder::stopped_event_ | Agent transfer | finish_if_stopped：Stopping 且 active_tasks_ 为零 | Forwarder::async_stop | 停止/重复等待；全部监听及会话任务排空 |
| Topology::finished_ | Node control | run 完成处理器；启动失败/未启动关闭 | Topology::close | 停止时；状态与 drain_error_ 另行表达结果 |

| MasterPath::opened | Node control / Master | 全部 Commit 确认；close_path 终止建立 | open_flow 的 Master 分支 | 当前一个建立等待者；每条路径一次 |
| MasterPath::released | Node control / Master | release_path：全部关闭确认、超时或停机终止 | close_flow 的 Master 分支 | 一个或多个；独立于本地失效通知和 opened |
| PendingOpen::completed | Node control / 入口 | FlowOpened 应答；epoch 变化、控制失败或停机 | open_flow 非 Master 分支 | 当前一个等待者；每个远端建立请求一次 |

### 优化前实现的成本（微基准基线）

- 尚无等待者的 notify_all 只设置标志并清空空列表，不创建工作线程或系统事件。
- 已触发后的 wait 直接返回，不构造 Waiter/channel、不排队恢复；仍经过 awaitable 的协程调用，帧可能由 Asio 回收缓存提供，并非语言层面绝对零成本。
- 真正挂起时：wait 协程保存一个 Waiter；Waiter 构造独立的 error_code channel 并登记 vector；async_receive 登记原生接收操作和独立取消；notify_all 为每个等待者提交完成任务。
- 当前 vendored Asio 的 error_code channel 使用默认 deque 容器。在本机 libstdc++ 中，即使容量为零且不存消息，构造该 channel 也会为 deque 分配内部存储。不能把 channel 的语义容量等同于零堆分配。
- vector 的取消移除是 O(W) 查找/移动；广播 O(W)，广播后 vector.clear，正常完成不再反复扫描旧列表。大量等待者分别取消且尚未广播时，累计可能 O(W²)。
- 唤醒通过同一执行器的队列完成，不等于跨控制/数据域切换，也不等于每次做一次操作系统线程切换。每个需要运行的等待者最终仍需一次执行机会，广播无法消除这个 O(W) 工作量。

### 微基准与原生关闭广播原型

环境为本机 AArch64、GCC/libstdc++、C++20、-O2 -DNDEBUG、仓库 vendored Asio 1.38.2、单 io_context(1)。现有项目 build 是 Debug；本微基准另行优化编译，不能将数值直接当作该 Debug 服务进程的耗时。预热后运行三次取中位数。分配统计同时覆盖全局 new 与 Asio 使用的 aligned_alloc；计时为带统计插桩的同机相对值。

完整轮次包含创建事件、启动等待协程、登记、通知、执行器调度及销毁，包含公共基准脚手架，不是生产代码一次 notify 的独立成本，也不是应用吞吐量测试。全部等待先登记后发通知；已经触发的快路单独测量。

原型在一个容量零的原生 channel 上接收，以 channel.close 广播；channel_closed 表示已完成，单次取消返回 false，is_open 快路保留迟到等待语义。它通过了现有 AsyncEvent 广播、独立取消、通知/取消先后及分阶段通知单测。只存在于 /tmp，不修改生产实现。

| 场景 | 优化前 AsyncEvent | 单 channel.close 原型 |
|---|---:|---:|
| 已触发后 wait | 约 54 ns | 约 51 ns |
| 1 等待者完整轮次 | 1.94 µs | 1.88 µs |
| 8 等待者完整轮次 | 11.34 µs | 10.22 µs |
| 64 等待者完整轮次 | 90.18 µs | 75.72 µs |
| 512 等待者完整轮次 | 958.94 µs | 678.45 µs |
| 512 等待者分别取消，完整轮次 | 1.43 ms | 1.38 ms |
| 512 次独立取消的同步提交阶段 | 259.77 µs | 634.24 µs |

已有事件的单等待者 notify_all 调用本身约 0.26 µs；已触发快路与只 co_return true 的协程基线约 49 ns 接近。快路预热后未观测到新的堆分配请求，但不代表每次协程调用不请求帧存储。

原型在高扇出广播时减少登记/分配，单等待者收益很小；其原生 cancel_by_key 也会扫描共享等待队列，不能指望它解决大量独立取消的最坏复杂度。不要把原生 timer.cancel 的广播基准当作等价替代：定时器取消不保留通知，且与取消等待操作使用相同错误码，缺少当前事件的锁存及胜出顺序语义。

本机对象与构造成本（执行器服务已预热，默认 allocator）：AsyncEvent 对象 88 字节、构造零堆分配；单 error_code channel 对象 232 字节，构造另有 2 次堆分配、请求 568 字节。原型即使没有等待者，也会常驻约 800 字节（不含分配器开销），当前 AsyncEvent 无等待时为 88 字节；当前一次等待后的 vector 通常仅保留 8 字节容量。不能只看广播时间就全量换成常驻 channel。

### 优化前的审计建议

当前没有证据表明这 14 处一次性事件限制了稳态转发吞吐，不建议新增一套通用通知框架或自写 Asio 完成/取消设施。现有 AsyncEvent 本身就是专用的一次性完成通知；先明确并统一这一个契约。

- 组件停止的 6 处低频完成等待保持简单，现有实现无需为了几次唤醒改写。
- 历史评估中的 SharedLink.completed_event 原本可能形成高扇出；第 22 节已随生产 Link 等待接口删除该事件，不再需要保留这一通知优化项。
- PendingOpen.completed、MasterPath.opened 是当前单等待者，若有明确的简化收益，可评估原生 channel/操作结果。但要保留取消与 epoch 变化时的结果优先级，不能只把 bool 换成 token。
- TCP Pair 的 attached 等待通常已经满足，约 50 ns 快路不值得以重新拆分公共 TCP/UDP 流程为代价消除。
- 如目标是稳态数据吞吐，优先观察 writable、send_space 和 receive_completed 的频率及等待时间；它们具有不同语义，不能纳入一次性广播机制。

### AsyncEvent 内部优化原型（2026-11-04）

本节记录落地前在 /tmp 的原型和测量，当时未改生产 AsyncEvent。优先评估内部存储，不新增公共通知类，也不自写 Asio 异步操作、取消或执行器工作管理。

1. **通知成功后释放等待者表容量。** 目前 clear 只清空元素，事件在一次性触发后仍保留 vector 的峰值容量。完成全部 try_send 后可用空 vector 交换释放存储。它保持通知顺序和现有接口，收益是长期存活事件不再保留无用容量；不应将其描述为通知速度优化。释放应放在全部提交成功之后，避免中途分配/提交异常时提前丢失尚未通知的登记。
2. **减少挂起等待者的 channel 内部空容器分配。** 当前 Asio 1.38.2 的 error_code channel 内嵌首个缓冲值，另外总会构造 traits 指定的 rest_ 容器。默认 deque 在本机空构造也分配两次、请求 568 字节。原型只对 AsyncEvent 私有的容量 1 通知 channel，通过 Asio 提供的 channel_traits::container/rebind 将容器配置为 std::list；空构造不分配，正常通知使用首值或直接交付，不创建链表节点。事件仍为 88 字节、构造零堆分配，没有新增 shared_ptr；恢复与独立取消仍使用原生 channel。该结论针对仓库当前 Asio 与本机标准库，不能据此替换承载业务消息的 channel 容器。
3. **独立取消可改为 O(1) 注销，但不是默认首选。** 等待者记录 vector 下标，以尾项交换后 pop_back，可消除大量分别取消时 O(W²) 的注销成本；代价是增加索引，并改变取消后剩余等待者的通知次序。如果需要保留登记顺序，则需要其他登记结构。当前正常广播已经先清空登记，恢复析构不会反复扫描原列表；索引方案对小扇出的完整耗时也没有稳定收益，不应仅为理论复杂度增加实现概念。

原型沿用上文同机优化微基准，预热后三次运行取中位数。以下完整轮次包含公共 co_spawn/post 脚手架，分配统计也包含脚手架，不能解释为生产每次 wait 的固定总分配次数；两实现每个挂起等待者恰好相差两次分配请求。

| 场景 | 优化前实现 | 只配置私有 channel 容器 |
|---|---:|---:|
| 1 等待者广播完整轮次 | 2.00 µs | 1.89 µs |
| 1 等待者完整轮次分配请求 | 6 次 / 1408 字节 | 4 次 / 840 字节 |
| 512 等待者广播完整轮次 | 0.979 ms | 0.792 ms |
| 512 等待者完整轮次分配请求 | 3593 次 / 962120 字节 | 2569 次 / 638600 字节 |

这些是带分配统计的局部测量，不能换算为应用吞吐提升。延迟会随运行负载波动，减少 2W 次分配比精确加速比例更有参考价值。保留已通知快路及原生异步恢复，不通过内联调用等待者来追求微小收益，否则会引入重入与销毁时序问题。

原实现、只释放容量、容器配置并释放容量、容器配置加索引并释放容量四组均通过现有测试语义：广播、重复通知、迟到等待、独立取消、先通知再取消、不同完成点互不唤醒。没有做提交异常注入，不宣称异常路径已穷尽验证；本轮未修改生产代码，未重复网络回归。

### AsyncEvent 两项优化落地与性能复评（2026-11-04）

本节是生产实现落地后的结论，上文的“当前实现”、未改生产代码及建议属于当时的审计/原型记录；比较优化方案时应以本节相同条件下的结果为准。

生产修改限定在 protocol/inc/async_event.h：私有 channel 用 Asio 提供的 ChannelTraits 容器扩展配置 std::list，保留原生完成、取消与调度；全部 try_send 成功后以空 vector 交换释放等待者登记容量。没有新增公共类型、shared_ptr、跨执行域任务或自定义异步操作，事件仍为 88 字节、构造零堆分配。独立取消仍沿用原来的登记顺序与 std::erase。

- 之前只优化 AsyncEvent、却拿默认容器的共享 channel 作对照并不充分。共享 channel 也配置相同容器后，其对象为 176 字节，服务预热后构造零堆分配；此前约 800 字节的常驻估算只适用于默认 deque 的旧原型，不再适用于这一候选。生产事件本体仍为 88 字节且仅挂起时构造等待者 channel。

- 当前实际使用多为停止/建立阶段的 0/1 等待，SharedLink 才可能积累多个等待者。复测支持先保留本轮两项优化；没有应用采样证明通知限制了稳态转发吞吐。后续若继续简化，应比较同样消除分配后的单 channel 方案并保留取消语义，无需新增通用通知框架。
