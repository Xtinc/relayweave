### 0.2 【中危・进程崩溃与信令丢失】`RelayEndpoint::from_params` 移出协程后，非法 `RelayOffer` / `RelayOpened` 会击穿 `transfer_io` 线程并丢失 `RelayReject` / `RelayCancel`

- **涉及代码**：
  - [agent/src/agent_session.cpp](../agent/src/agent_session.cpp)（第 8–25 行 `RelayEndpoint::from_params`、第 118–122 行 `AgentSession::handle`）
  - [agent/src/forwarder.cpp](../agent/src/forwarder.cpp)（第 344–395 行 `Forwarder::relay_message`）
  - [agent/src/agent_control.cpp](../agent/src/agent_control.cpp)（第 220–225 行 `AgentControl::handle_control_message`）
  - [agent/src/main.cpp](../agent/src/main.cpp)（第 74–77 行 `transfer_io.run()`）
- **缺陷机理**：
  1. **重构前（`bb4415d` 之前）**：收到 `RelayOffer` 或 `RelayOpened` 时仅保存原始 JSON，字段合法性校验（`data_address`、`data_port`、`uuid`、`ticket`、`session_id`、`tls_framing`）在 `AgentSession::attach()` 协程内执行。若参数非法抛出 `std::invalid_argument`（如 `Unsupported TLS data framing` 或 `data_port` 越界），会被 `AgentSession::run()` 的 `try / catch` 捕获，调用 `fail(...)` 并向 Node 发送 `RelayReject`（Producer）或 `RelayCancel`（Consumer）以释放 Node 侧配额。
  2. **重构后（`bb4415d`）**：`RelayEndpoint::from_params(p, protocol)` 被移至 `Forwarder::relay_message()`（处理 `RelayOffer`）和 `AgentSession::handle()`（处理 `RelayOpened`）中同步调用。而 `relay_message()` 是由 `AgentControl::handle_control_message()` 通过无异常捕获的 `asio::post(transfer_executor_, ...)` 投递执行的：
     - **进程级崩溃风险**：一旦 `from_params`（或 `AgentSession::handle` 中的 `config::optional_string`）因报文参数异常抛出 `std::invalid_argument`，在 `transfer_io` 调用栈上没有任何 `try / catch` 保护，异常会直接逃逸出 `transfer_io.run()` 所在的工作线程 lambda，触发 C++ `std::terminate()` 导致整个 Agent 进程崩溃。
     - **信令与状态机悬挂**：即便在外层补充异常捕获，若 `RelayOffer` 在创建会话前因 `from_params` 失败退出，将不会向 Node 发送 `RelayReject`；若 Consumer 的 `RelayOpened` 在 `AgentSession::handle` 中因 `from_params` 抛异常而未调用 `fail()` / `changed.cancel()`，`AgentSession::run()` 会一直在 `changed.async_wait` 上挂起直至建立超时，且无法及时向 Node 发送 `RelayCancel`。

### 0.3 【低～中危・代码细节与边界隐患】`NodeSession` 构造顺序及多跳 TCP 短读窗口放大

- **涉及代码**：
  - [node/src/node_session.cpp](../node/src/node_session.cpp)（第 4–19 行）
  - [node/src/pipeline_mgr.cpp](../node/src/pipeline_mgr.cpp)（第 218–228 行）
  - [protocol/src/flow_protocol.cpp](../protocol/src/flow_protocol.cpp)（第 708–748 行）
- **隐患表现**：
  1. **`NodeSession` 构造函数的 `use-after-move` 与成员初始化顺序倒置**：
     ```cpp
     NodeSession::NodeSession(RelayNode &node, const AgentPeer &session, RelayRequest params, bool ingress,
                             SRVTrafficPtr traffic)
         : node_(node), control_(std::in_place_type<ControlRouterMulti>, *this, session, std::move(params), ingress),
           traffic_(std::move(traffic))
     {
         select_data(params.protocol);
     }
     ```
     在成员初始化列表中已经对 `params` 执行了 `std::move(params)` 传给 `ControlRouterMulti` / `ControlRouterSingle` 的按值形参，随后在构造函数体内又读取已移动对象 `params.protocol`。虽然 `protocol` 是枚举类型因此值未受损，但触发了典型的 `use-after-move` 代码异味；同时在 `control_` 构造期间 `data_` 尚未初始化（处于默认的 `TcpPipeline *(nullptr)` 状态），若控制器构造函数内调用 `relay_.protocol()` 将返回错误的默认协议。
  2. **多跳 TCP 小包场景下的本地 320 KiB 窗口放大效应**：
     在提交 `393350a` 中，`StreamPipeline<TcpTransport>::read_remote_pair()` 每次固定分配 32 KiB 的 `PooledBuffer` 供 `async_read_some` 读取，短读后调用 `data.truncate(received)`。由于 `FlowProtocol::Stream::try_send()` 与 `route()` 按完整分配容量 `data->capacity()`（即 `32768 + 128 = 32896` 字节）计入 `direction.buffered_bytes`（上限 `flow_window_bytes = 320 KiB`），当业务为 SSH 交互或高频小包（如每次读取 64 字节）且下游 `NodeLink` 存在排队时，**仅积压 9 个 64 字节小包（共 576 字节有效数据）就会占满 320 KiB 本地缓冲预算**并阻塞入口读取。
  3. **`StreamPipeline<TcpTransport>::read_remote_pair` 缺少非 EOF 零字节读取防护**：
     对比 [protocol/src/xfr_channel.cpp](../protocol/src/xfr_channel.cpp) 第 271 行的 `if (!error && size == 0) continue;`，`read_remote_pair()`（[node/src/pipeline_mgr.cpp](../node/src/pipeline_mgr.cpp) 第 221–235 行）在 `!error && received == 0` 时未做 `continue` 保护，会直接当作 `size == 0` 发送 `finish_send()`（FIN）。

## 二、 明显的架构与实现缺陷复查（Defects & Risks）

### 2.1 【高危可用性缺陷】Master 控制出站队列满（容量 100）会触发 Master 自杀停机 —— 【仍然存在】

- **复查状态**：**按既定设计保留满队列停机语义，但用于防止正常并发触发满队列的“集群消息预算与准入控制（改进项 07）”尚未实施**。
- **代码定位**：
  - [node/src/cluster_mgr.cpp](../node/src/cluster_mgr.cpp) 第 758–766 行、第 708–720 行
  - [node/src/relay_node.cpp](../node/src/relay_node.cpp) 第 264–280 行
- **当前风险**：
  在 `ClusterMgr::send()` 中，Master 本地发起的所有集群消息（包括 `TopologyMembers`、`ServiceLookup` 广播，以及每条多跳 Flow 的 `LinkPrepare` / `FlowPrepare` / `FlowCommit` / `FlowClose` 逐跳单播）仍需先进入容量为 `channel.max_queued_messages`（默认 **100**）的 `outbound_channel_`：
  ```cpp
  if (config_.role == ClusterConfig::Role::Master)
  {
      if (outbound_channel_.try_send(asio::error_code{}, std::move(message)))
      {
          return SendResult::Submitted;
      }
      fail("master control outbound queue full");
      return SendResult::QueueFull;
  }
  ```
  目前尚未对并发建流事务实施基于队列容量的消息预算准入控制或分批推进。当同一 `control_io` 事件循环周期内并发多跳建流/关闭突发消息超过 100 条（尚未交出协程供 `deliver_messages` 消费）时，Master 仍会立即触发 `fail("master control outbound queue full")` 关停自身进程。

### 2.5 【协议状态机与资源泄漏缺陷】多跳收尾无限期等待与 UDP 会话缺陷 —— 【部分解决】

- **复查状态**：**2026-10-31 已修复普通 Agent UDP 多客户端隔离并加入 idle；Node 通用 idle 与多跳 Finished 期限独立保留**。
- **代码定位**：
  - [node/src/control_router_multi.cpp](../node/src/control_router_multi.cpp) 第 376–382 行
  - [node/src/datagram_mgr.cpp](../node/src/datagram_mgr.cpp) 第 200–206 行
  - [agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 209–215 行
- **缺陷机理**：
  1. **`ControlRouterMulti` 传输完成后的无超时死等（仍然存在）**：
     在 `ControlRouterMulti::establish_and_transfer()`（第 376–382 行）中：
     ```cpp
     co_await relay_.bridge();
     send_peer(CtrlCommand::RelayPeerFinished, njson::object());
     while (!peer_finished_ && !stop_requested_)
     {
         changed_.expires_at(Clock::time_point::max());
         co_await changed_.async_wait(use_nothrow_awaitable);
     }
     ```
     当本端 `bridge()` 读写循环全部结束并发送 `RelayPeerFinished` 后，使用 `Clock::time_point::max()` 无限期等待对端的 `RelayPeerFinished`。若对端因本地应用半关闭挂起（迟迟不关写端）而未完成 `bridge()`，本端 `NodeSession` 与整条 `Flow` 在链路与控制连接正常期间将一直占用配额。
  2. **UDP 会话空闲超时（Idle Timeout）（普通 Agent 已解决，Node 通用 idle 仍保留）**：
     Consumer Agent 按双向有效业务活动执行 idle 回收，通过现有 cancel 链路释放两端 Agent、目标 socket、Node 配对和 Flow。直接接入 Node、长期不取消的其他客户端仍无 Node 通用 idle；`DatagramMgr::run_local_pair()` 继续等待 `pair->finished`。
  3. **Agent 本地 UDP Forwarder 的源地址锁定与同 IP 端口互相覆盖（已解决）**：
     原单个 `forward.local_peer` 锁定首个源 IP，并被同 IP 不同端口覆盖，导致回包串线。现按监听器与完整源 endpoint 索引独立 AgentSession，固定回包 endpoint；Producer 沿用每会话独立目标 socket，Node session/Flow 协议不变。首包触发按需建立，建立期间只保存首包并丢弃后续包，attach 完成且 ready 后发送首包再开放正常转发。共享容量、建立并发和 idle 约束见[改进计划第 12 节](缺陷改进计划.md)。
