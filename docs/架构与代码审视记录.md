# RelayWeave 架构与代码审视记录（Agent & Node）

本文档基于当前 `agent/`、`node/` 与 `protocol/` 目录下的实际 C++20 源码实现，对系统在**架构分层、控制协议、数据面流转、并发执行域及异常处理**等方面存在的**过度冗余设计**与**明显缺陷/隐患**进行系统性盘点，并给出可落地的演进与重构建议。

## 一、 过于冗余的设计与实现（Redundancies）

### 1.1 Agent 控制连接层的退化包装与废弃协议路径

- **涉及代码**：
  - [agent/inc/node_connection.h](../agent/inc/node_connection.h) / [agent/src/node_connection.cpp](../agent/src/node_connection.cpp)
  - [agent/src/agent_control.cpp](../agent/src/agent_control.cpp)
  - [node/src/node_control.cpp](../node/src/node_control.cpp)
- **冗余表现**：
  1. **`NodeConnectionMgr` 形同虚设**：
     早期设计意图是由 `NodeConnectionMgr` 维护到多个入口 Node 的控制连接池，但当前架构演进为“Agent 仅维护唯一一条到主控 Node（Primary Node）的长连接，跨入口控制消息全部由主控 Node 经集群转发”。因此，`NodeConnectionMgr` 内部仅持有一个 `std::unique_ptr<NodeConnection> primary_`，其 `start()`、`stop()`、`close()`、`primary()` 全部是对 `primary_` 的一比一薄转发，多出一层毫无实质职责的对象包装与异步生命周期状态（`stopped_event_`、`stopping_`）。
  2. **废弃的 `NodeLookup` / `NodeLocated` / `NodeError` 协议分支**：
     在 [node/src/node_control.cpp](../node/src/node_control.cpp)（第 153–155、182–187、388–427 行）及 [protocol/inc/message.h](../protocol/inc/message.h) 中完整实现了 `node.lookup` 的客户端请求处理、集群单播转发与回包逻辑；但在整个 `agent/` 代码库中，**没有任何地方发送 `NodeLookup`**。
  3. **已校验却未使用的控制端口字段**：
     `NodeControl::service_location()` 在 `service.located` 中下发了目标节点的控制 `port`，`AgentControl::locate_service()`（[agent/src/agent_control.cpp](../agent/src/agent_control.cpp) 第 150 行）解析并校验了 `port`，随后直接丢弃（仅将 `address` 传给 ICMP `ProbeSet`），因为 Agent 根本不会直连目标或入口 Node 的控制端口。

### 1.2 `StreamPipeline` 与 `DatagramMgr` 的双套状态机重复，以及 `NodeSession` 的高频跨域 `co_spawn`

- **涉及代码**：

     - 尤其是 `activate()`（第 162–170 行），仅仅是在传输域把布尔值 `endpoint->active = true` 置位，却为此专门发起了一次跨线程 `co_spawn(..., asio::use_awaitable)` 同步等待。

## 二、 明显的架构与实现缺陷（Defects & Risks）

### 2.1 【高危可用性缺陷】Master 控制出站队列满（容量 100）会触发 Master 自杀停机

- **代码定位**：
  - [node/src/cluster_mgr.cpp](../node/src/cluster_mgr.cpp) 第 544–552 行、第 602–607 行
  - [node/src/relay_node.cpp](../node/src/relay_node.cpp) 第 251–267 行
- **缺陷机理**：
  在 `ClusterMgr::send()` 中，当节点角色为 Master 时，所有发往集群的消息（包括 `TopologyMembers` 广播、`ServiceLookup` 广播、以及每个多跳 Flow 的 `LinkPrepare` / `FlowPrepare` / `FlowCommit` / `FlowClose` 逐节点单播）都要先塞入一个容量仅为 `channel.max_queued_messages`（默认 **100**）的 `outbound_channel_`：
  ```cpp
  if (config_.role == ClusterConfig::Role::Master)
  {
      if (outbound_channel_.try_send(asio::error_code{}, std::move(message)))
      {
          return SendResult::Submitted;
      }
      fail("master control outbound queue full");
      return SendResult::QueueFull;
  }
  ```
  一旦 `outbound_channel_.try_send` 返回 `false`（例如在同一个 `control_io` 事件循环周期内，20 个并发多跳请求同时触发 5 节点 `FlowPrepare`，瞬间产生 $20 \times 5 = 100$ 条消息，尚未切换到 `deliver_messages` 协程消费），Master 立即调用 `fail("master control outbound queue full")`！
  `fail()` 会关闭 Master 监听器并调用 `RelayNode::cluster_failed()`，将 Master 置为 `Stopping`，清空全网 Flow，并通知主线程退出进程。
- **根因反思**：
  `ClusterMgr::send()` 与 `deliver_messages()` **本就运行在同一个单线程 `control_io` 上**，且每个 `ClusterSession` 内部的 `TLSChannel` 已经拥有各自独立的 `write_channel_` 发送队列。在 Master 内部额外串联一个容量仅 100 的 `outbound_channel_`，并在满载时直接让整个 Master 进程崩溃自杀，是严重的单点脆弱性缺陷。

### 2.2 【性能与扩展性缺陷】控制面核心路径存在大量 $O(N)$ 全表线性扫描

- **代码定位**：
  - [node/src/relay_node.cpp](../node/src/relay_node.cpp) 第 360–491 行
  - [agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 354–396 行
  - [node/src/cluster_mgr.cpp](../node/src/cluster_mgr.cpp) 第 105–110 行
- **缺陷机理**：
  1. **`RelayNode::relay_sessions_` 使用 `std::vector` 顺序存储并高频全表扫描**：
     - **准入计数扫描**：每次新建会话调用 `start_relay()`（第 360–373 行），都执行两次 `std::ranges::count_if` 全表扫描统计 `is_multi()` 数量和对应 `protocol()` 数量；且删除会话时使用 `std::erase(self->relay_sessions_, relay)` 触发 $O(N)$ 内存搬移。
     - **信令路由扫描**：每次收到 `RelayCancel`、`RelayReject`、重传的 `RelayOpen`，或者集群单播过来的 `RelayPeerOpen` / `RelayPeerAttached` / `RelayPeerReady` / `RelayPeerFinished` / `RelayPeerClose`（第 395、417、456 行），都会遍历整个 `relay_sessions_` vector，逐一调用 `relay->handle(...)` 或 `relay->handle_peer(...)`。当并发会话达到上千条时，控制面消息处理复杂度退化为 $O(N^2)$。
  2. **`Forwarder::relay_message()` 线性遍历 `relays_` map**：
     `Forwarder` 仅以本地 `request_id` 作为 `std::map` 的键；当收到 `RelayOffer`（去重检查）或收到按 `uuid` 标识的 `RelayReady`、`RelayClosed`、`RelayError` 时（[agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 358、377 行），只能遍历整个 `relays_` 容器比对 `endpoint.at("uuid")`。
  3. **`ClusterRoom` 成员查找线性扫描**：
     `ClusterRoom` 使用 `std::set<std::shared_ptr<ClusterParticipant>>` 保存成员，每次单播转发 `deliver()`（[node/src/cluster_mgr.cpp](../node/src/cluster_mgr.cpp) 第 105 行）都用 `std::ranges::find_if` 线性比对 `node_id()`，而非使用 `std::unordered_map<std::string, ...>`。

---

### 2.3 【高可用与广播风暴缺陷】主控连接单点强绑定与全集群广播放大

- **代码定位**：
  - [agent/src/agent_control.cpp](../agent/src/agent_control.cpp) 第 113–127 行、第 240–264 行
  - [node/src/node_control.cpp](../node/src/node_control.cpp) 第 238–246 行、第 300–310 行
- **缺陷机理**：
  1. **主控 Node 闪断会无差别杀死所有跨节点存活数据流**：
     Consumer Agent 的所有控制信令均通过唯一的主控连接（`primary_`）代转。当主控 Node 重启或控制连接因瞬时网络抖动断开时，`AgentControl::connection_closed()` 立即触发 `forwarder.control_disconnected()`（[agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 131–142 行），将本地所有正在传输数据的 `AgentSession` 全部 `cancel("primary control disconnected")`！即便某条 SSH/数据库长连接的数据流实际走的是 `Agent -> Node-A -> Node-B`，完全不经过主控 Node 的数据面，也会因为主控信令连接闪断而被强制掐断。
  2. **`TopologyQuery` 与 `ServiceLookup` 盲目使用全集群广播**：
     - 在 `NodeControl::report_topology()`（[node/src/node_control.cpp](../node/src/node_control.cpp) 第 300–310 行）中，当 Slave 节点收到 Agent 的 `TopologyQuery` 时，明明只有 Master 能生成拓扑快照，且本地可以通过 `topology_.master_id()` 知道谁是 Master，代码却调用 `broadcast_client_query()` 向**全集群所有节点广播 `TopologyQuery`**，其他 Slave 收到后再忽略。
     - 同样，`ServiceLookup` 在本地未命中时直接全集群广播；当某个配置在 `forwards` 中的服务尚未启动时，每个 Consumer Agent 每 5 秒轮询一次 `query_services(true)`，在集群内造成持续的 $O(K \times M)$ 广播流量放大。

### 2.4 【安全与传输架构缺陷】多跳 TLS 业务在节点间退化为明文，且 `handle_topology_snapshot` 源校验被注释

- **代码定位**：
  - [node/src/pipeline_mgr.cpp](../node/src/pipeline_mgr.cpp) 第 35–44 行、第 240–245 行
  - [node/src/nodelink_mgr.cpp](../node/src/nodelink_mgr.cpp) 第 421 行
  - [protocol/src/lnk_channel.cpp](../protocol/src/lnk_channel.cpp)
  - [node/src/node_control.cpp](../node/src/node_control.cpp) 第 326–329 行
- **缺陷机理**：
  1. **多跳 `tls` 服务在跨节点 `NodeLink` 上完全明文裸奔**：
     当服务配置为 `"protocol": "tls"` 并经过多跳中继（`Agent -> Ingress Node -> Relay Node -> Egress Node -> Agent`）时：
     - Consumer Agent 与 Ingress Node（18446 端口）之间建立了 TLS，但 Ingress Node 的 `TlsPipeline` 将 TLS 解密成明文后写入 `FlowStream`；
     - `Ingress Node -> Relay Node -> Egress Node` 之间的 `NodeLink`（18448 端口）使用的是**无任何加密与完整性校验（MAC）的普通 TCP Socket**！
     - 这导致跨地域公网骨干网上传输的是完全明文的业务载荷。这不仅违背了用户配置 `"protocol": "tls"` 的安全预期，而且中间网络攻击者只需根据 32 字节明文 `LnkFrameHeader` 即可伪造 `Reset` 或 `Fin` 帧任意切断业务流。
  2. **`handle_topology_snapshot` 的 Master 身份校验被注释**：
     在 [node/src/node_control.cpp](../node/src/node_control.cpp) 第 326–329 行：
     ```cpp
     void NodeControl::handle_topology_snapshot(CtrlMessage message)
     {
         // if (message.params->at("source") != topology_.master_id())
         // {
         //     return;
         // }
     ```
     校验发送源是否为当前 Master 的关键代码被注释掉，导致任何集群节点均可向请求方伪造拓扑快照。

### 2.5 【协议状态机与资源泄漏缺陷】多跳收尾无限期等待与 UDP 会话缺陷

- **代码定位**：
  - [node/src/control_router_multi.cpp](../node/src/control_router_multi.cpp) 第 374–380 行
  - [node/src/datagram_mgr.cpp](../node/src/datagram_mgr.cpp) 第 225–231 行
  - [agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 206–212 行
- **缺陷机理**：
  1. **`ControlRouterMulti` 传输完成后的无超时死等**：
     在 `ControlRouterMulti::establish_and_transfer()`（第 374–380 行）中：
     ```cpp
     co_await relay_.bridge();
     send_peer(CtrlCommand::RelayPeerFinished, njson::object());
     while (!peer_finished_ && !stop_requested_)
     {
         changed_.expires_at(Clock::time_point::max());
         co_await changed_.async_wait(use_nothrow_awaitable);
     }
     ```
     当本端 `bridge()` 读写循环全部结束并发送 `RelayPeerFinished` 后，使用 `Clock::time_point::max()` **无限期等待对端的 `RelayPeerFinished`**。若对端因本地应用半关闭挂起（迟迟不关写端）或集群单播消息丢失，本端 `NodeSession` 与整条 `Flow` 将永久僵死，无法进入 `close_flow()`，持续侵占 `max_relays` 与 `max_flow_count`（上限 1000）配额。
  2. **UDP 会话缺乏空闲超时（Idle Timeout）**：
     `DatagramMgr::run_local_pair()`（第 225 行）仅等待 `pair->finished.wait()`，而 UDP 数据面没有任何空闲超时淘汰机制；只要控制连接不断开且服务不下线，单次建立的 UDP 中继配对将永久驻留。
  3. **Agent 本地 UDP Forwarder 的源地址锁定与端口互相覆盖 Bug**：
     在 `Forwarder::receive_local_datagrams()`（[agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 206–212 行）中：
     ```cpp
     if (size > DatagramHeader::maximum_user_payload ||
         (forward.local_peer && forward.local_peer->address() != source.address()))
     {
         continue;
     }
     forward.local_peer = source;
     ```
     - 一旦第一个本地客户端发包，`forward.local_peer` 即永久锁定该源 IP（后续即便该客户端早已退出，其他 IP 的客户端发包也会被永久丢弃）；
     - 若同一台机器（同 IP `127.0.0.1`）上的两个本地进程（不同临时源端口）并发向该 UDP 监听端口发包，`forward.local_peer` 的端口会被后发包的进程覆盖，导致前一个进程的回包全部错发给后一个进程。

### 2.6 【内存开销与系统调优缺陷】协程帧内嵌 64KB 缓冲数组与 `SCHED_RR` 实时线程隐患

- **代码定位**：
  - [node/src/pipeline_mgr.cpp](../node/src/pipeline_mgr.cpp) 第 234 行
  - [protocol/src/xfr_channel.cpp](../protocol/src/xfr_channel.cpp) 第 22–44 行、第 159、250、323、358 行
  - [agent/src/forwarder.cpp](../agent/src/forwarder.cpp) 第 189、458 行
- **缺陷机理**：
  1. **C++20 协程帧内嵌 64KB 大数组导致常驻堆内存膨胀与额外拷贝**：
     在 `StreamPipeline::read_remote_pair`（第 234 行）、`transfer_tls`（第 250 行）等协程函数中，局部变量直接声明了 `std::array<std::uint8_t, 65467> buffer;`。在 C++20 无栈协程中，跨越 `co_await` 挂起点的局部变量直接分配在堆上的协程帧（Coroutine Frame）内。
     - 这意味着每条活跃的多跳连接仅在读协程帧上就固定占用 **64 KB** 内存；
     - 对于 `read_remote_pair` 中的 TCP 流，数据先由内核拷贝到这个 64 KB 协程帧数组中，紧接着在第 259 行调用 `endpoint->flow->copy_payload({buffer.data(), size})` 从 PMR 池分配内存并再做一次 `std::memcpy`。如果直接从 PMR 池分配块读入并调用 `PooledBuffer::slice(0, size)`，既能将协程帧缩小到百字节级，又能彻底消除这次 64 KB 内存拷贝。
  2. **传输线程盲目设置 `SCHED_RR` 实时优先级（98）与遗留线程名 `"audio_thd"`**：
     在 `set_current_thread_scheduler_policy()`（[protocol/src/xfr_channel.cpp](../protocol/src/xfr_channel.cpp) 第 22–44 行）中：
     - 将 `transfer_tcp_io`、`transfer_udp_io` 线程设置为 Linux 实时调度策略 `SCHED_RR` 且优先级高达 `max_priority - 1`（98）；当容器或进程具备 `CAP_SYS_NICE` 权限且遭遇大流量突发时，实时传输线程会 100% 抢占 CPU，直接饿死同核上运行普通优先级的 `control_io`（导致心跳超时断连）与 `cluster_data_io`（导致 `FlowProtocol` 无法消费队列）！
     - 第 42 行硬编码 `pthread_setname_np(thread, "audio_thd");`，属于明显的外部项目遗留代码。

## 三、 审视汇总与改进优先级路线图

| 优先级 | 问题分类 | 改进项 | 核心收益 |
|---|---|---|---|
| **P0 (紧急)** | 可用性缺陷 | **移除 Master `ClusterMgr` 中容量 100 的 `outbound_channel_` 自杀逻辑**：在 `control_io` 上直接分发至各 `ClusterParticipant` 的 `TLSChannel` 队列；取消满队列即关停整个 Master 的行为。 | 消除高并发建流或广播时 Master 节点直接崩溃退出的致命风险。 |
| **P0 (紧急)** | 系统稳定性 | **修正 `set_current_thread_scheduler_policy()`**：移除 `SCHED_RR` 98 优先级（或改为温和的 nice 值调整），修正 `"audio_thd"` 线程命名。 | 防止高负载下传输线程饿死 `control_io` 与 `cluster_data_io` 引发全网断连。 |
| **P0 (紧急)** | 资源泄漏风险 | **为 `ControlRouterMulti` 尾部等待 `peer_finished_` 增加有限超时（如 10~30s）**，恢复 `NodeControl::handle_topology_snapshot` 的 Master 源校验。 | 防止对端半关闭挂起或丢包导致 `NodeSession` 与 `Flow` 永久泄漏。 |
| **P1 (重要)** | 控制面性能 | **将 `RelayNode::relay_sessions_` 替换为哈希索引容器**（按 `(session, request_id)`、`uuid`、`(epoch, flow_id)` 索引，并维护 O(1) 协议活跃计数器）；`Forwarder::relays_` 引入 `uuid` 二级索引；`ClusterRoom` 改用 `unordered_map` 索引 `node_id`。 | 将控制面信令分派与容量检查从 $O(N)$ 全表扫描降至 $O(1)$。 |
| **P1 (重要)** | 内存与零拷贝 | **重构 `StreamPipeline::read_remote_pair`**：直接分配 `PooledBuffer` 供 Socket `async_read_some` 写入，并用 `PooledBuffer::slice(0, size)` 截断。 | 消除每个连接 64 KB 的协程帧内存开销，并省去入口处一次 `memcpy`。 |
| **P1 (重要)** | 协议广播收敛 | **`TopologyQuery` 改为定向单播发往 `topology_.master_id()`**；Master 在 `TopologyMembers` 或集中目录中同步服务位置，避免未命中时全网高频广播 `ServiceLookup`。 | 大幅降低集群控制面背景流量。 |
| **P2 (架构演进)** | 冗余清理与解耦 | 1. 合并 `NodeConnectionMgr` 与 `NodeConnection`，清理未使用的 `NodeLookup` 死代码；<br>2. 抽取 `StreamPipeline` 与 `DatagramMgr` 公共配对基类，合并 `NodeSession` 中的细碎 `co_spawn`；<br>3. 将 `NodeLinkMgr` 中的 `njson` 内部状态替换为强类型结构体。 | 显著精简代码量，降低维护心智负担与跨执行域调度开销。 |
| **P2 (安全与功能)** | 数据面安全与 UDP | 1. 支持多跳 `tls` 端到端加密透传或为 `NodeLink` 增加轻量 AEAD 加密；<br>2. 为 Agent 本地 UDP Forwarder 增加多客户端端口映射表与空闲超时回收。 | 补齐跨公网多跳传输安全性与 UDP 多客户端并发能力。 |
